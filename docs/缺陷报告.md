来源：接口测试探索过程实测（被测系统 mall-tiny commit `a81ec47`，本机与容器化环境）。
所有证据均为真实请求/响应摘录，复现步骤可直接执行。

## BUG-001 用户列表与注册接口响应泄露 BCrypt 密码哈希

- **级别**：严重（安全）
- **模块**：用户管理
- **复现**：
  1. `POST /admin/login` 获取管理员 Token
  2. `GET /admin/list?pageNum=1&pageSize=5`（带 Token）
  3. 观察响应 `data.list[].password` 字段
- **实际结果**：每个用户的 BCrypt 哈希随响应返回
  `"password":"$2a$10$sDy/XFB0D/2trdE5GLUYUOqqrQ9dJDM0R4lROzHTtOxlk8w5UJJHO"`
  注册接口（`POST /admin/register`）的响应同样返回哈希
- **期望结果**：密码哈希属于敏感凭据材料，列表/注册响应不应包含 password 字段
- **影响**：拖库级别信息暴露面扩大。BCrypt 虽难逆向，但攻击者获得哈希后可离线
  撞库弱口令；同时哈希外泄扩大了内部信息暴露面
- **建议**：列表与注册响应使用不含 password 字段的 DTO；注册响应仅返回 id/username

## BUG-002 更新用户状态接口对不存在的 id 返回 HTTP 500

- **级别**：一般（健壮性）
- **模块**：用户管理
- **复现**：`POST /admin/updateStatus/197609?status=0`（带管理员 Token，197609 为不存在的 id）
- **实际结果**：HTTP 500 + Spring 默认错误体
  `{"timestamp":"...","status":500,"error":"Internal Server Error","path":"/admin/updateStatus/197609"}`
- **期望结果**：资源不存在应返回业务错误（参照项目惯例 code 404/500 + 明确 message），
  不应出现未处理异常
- **影响**：畸形/伪造请求可触发服务端异常，异常日志噪音干扰排障；与同模块
  delete 接口（不存在 id 返回业务码 500）行为不一致，客户端难以统一处理
- **建议**：update 前校验记录存在性，返回业务失败码；补充对不存在 id 的接口测试

## BUG-003 分配角色接口对不存在的 adminId 静默成功并写入孤儿关系行

- **级别**：一般（数据一致性）
- **模块**：权限分配
- **复现**：`POST /admin/role/update?adminId=197609&roleIds=9`（adminId 不存在）
- **实际结果**：返回 `{"code":200,"message":"操作成功","data":1}`，
  且 `ums_admin_role_relation` 中写入了一条 admin_id=197609 的关系行
- **期望结果**：adminId 不存在应返回业务失败；不应为不存在的用户写入关系数据
- **影响**：孤儿关系数据污染权限体系；依赖关系表做权限联查时可能引入脏数据
- **建议**：分配前校验 adminId 与 roleIds 的存在性

## BUG-004 同模块错误处理风格不一致：delete 返回业务码、updateStatus 返回 HTTP 500

- **级别**：建议（一致性）
- **模块**：用户管理
- **复现**：对不存在的资源 id 分别调用 `POST /admin/delete/{id}` 与
  `POST /admin/updateStatus/{id}?status=0`
- **实际结果**：delete → HTTP 200 + `{"code":500,"message":"操作失败"}`；
  updateStatus → HTTP 500 + Spring 默认错误体
- **期望结果**：同类"资源不存在"场景应有统一的错误契约（HTTP 状态与响应结构一致）
- **影响**：客户端需要为同模块的同类错误写两套处理逻辑；违背项目
  "业务失败恒 HTTP 200 + 业务码"的既有约定
- **建议**：统一走全局异常处理与业务码规范

## BUG-005 登录失败提示可枚举有效用户名

- **级别**：一般（安全）
- **模块**：认证
- **复现**：
  1. `POST /admin/login`，username=admin（存在），password 错误 →
     `{"code":500,"message":"密码不正确"}`
  2. `POST /admin/login`，username=no_such_user（不存在）→
     `{"code":404,"message":"用户名或密码错误"}`
- **实际结果**：两种失败场景的消息可区分，攻击者可凭消息差异确认
  "某用户名存在"，进而对存在的账号定向爆破
- **期望结果**：两种场景统一返回"用户名或密码错误"（防撞库标准做法）
- **影响**：降低撞库/爆破成本
- **建议**：统一失败提示；补充登录失败次数限制

## IMP-001 容器化部署存在环境漂移缺陷（已在本项目修复）

- **级别**：建议（部署）
- **现象与修复**：
  1. MySQL 官方镜像 init 脚本导入中文种子数据未声明连接字符集，
     入库即乱码（"超级管理员" 存为 `è¶…çº§ç®¡ç†å'˜`）→
     初始化脚本增加 `SET NAMES utf8mb4`
  2. 容器默认 POSIX locale 使 Bean Validation 消息退化为英文
     （"must not be empty"），与本机中文环境行为不一致 →
     应用增加 `JAVA_TOOL_OPTIONS=-Duser.language=zh -Duser.country=CN`
- **影响**：环境漂移导致"同样的代码、不同的行为"，测试结果不可信
- **建议**：将字符集与 locale 显式固化进部署配置；这类差异应纳入
  环境验收检查项
